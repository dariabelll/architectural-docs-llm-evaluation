# Reference Facts: OpenTelemetry Collector (core)

Source commit: 7b425533dfa04ff0a0d3b384381979e945a69b2a
Created from source code inspection (no project documentation used as source).

## Major components and responsibilities

- F1. `otelcol.Collector` (otelcol/collector.go) is the top-level runtime object: `NewCollector` builds it, `Run(ctx)` performs startup (`setupConfigurationComponents`) and then blocks in a control loop (`LOOP`, collector.go:414-493) selecting over config-watch events, async errors, OS signals, the shutdown channel, and `ctx.Done()`.
- F2. Collector lifecycle states are `StateStarting`, `StateRunning`, `StateClosing`, `StateClosed` (otelcol/collector.go:32-37), stored in an `atomic.Int64` and changed by `setCollectorState`.
- F3. Configuration loading is done by `ConfigProvider`, a thin wrapper over `confmap.Resolver` (otelcol/configprovider.go:24-49): `getWithConf` resolves the conf, then `unmarshal`s it into `Config` with component factories (configprovider.go:64-87).
- F4. `confmap.Resolver.Resolve` (confmap/resolver.go:164-210) retrieves configuration from each configured URI in order, merges the maps, captures a pre-expansion view (`unexpandedConfMap`), expands `${...}` references recursively, escapes `$$`, and then applies converters in order.
- F5. Providers are registered per URI scheme, validated for a unique, well-formed scheme; `DefaultScheme`, if set, must exist among providers (confmap/resolver.go:105-126). `cmd/otelcorecol/main.go` registers `env`, `file`, `http`, `https`, `yaml` providers.
- F6. `Resolver.Watch()` exposes a channel signalled by provider `onChange` events; the Collector's control loop reacts to `configProvider.Watch()` by calling `reloadConfiguration` (confmap/resolver.go:258-280, otelcol/collector.go:464-471).
- F7. Reloading: a full reload shuts down the running service and rebuilds it (`reloadConfiguration`, otelcol/collector.go:289-322); a partial receiver-only reload is attempted first when feature gates `service.partialReload` (Alpha) and `service.partialReloadReceivers` (Beta) are both enabled (`ReceiverPartialReloadEnabled`, service/service.go:264-267; `tryPartialReceiverReload`, collector.go:328-364), falling back to full reload on failure.
- F8. `service.New` (service/service.go:108-224) creates the `Service`: it builds `graph.Host` holding component builders, requires a non-nil `TelemetryFactory`, creates the shared telemetry `Resource`, then logger, meter provider, and tracer provider, initializes the pipeline graph (`initGraph`) and extensions (`initExtensions`), and registers process metrics on supported OSes only (service.go:392-412).
- F9. `Service.Start` order is: start extensions → notify extensions of the config snapshot → start all pipelines → notify extensions the pipeline is ready (service/service.go:232-258).
- F10. `Service.Shutdown` order is: notify pipeline not ready → shut down pipelines → shut down extensions → shut down tracer provider, meter provider, logger (reverse of creation) (service/service.go:289-323).
- F11. The pipeline DAG is built by `graph.Build` in service/internal/graph/graph.go:78-97: create nodes for every component instance, create edges, then instantiate components in `buildComponents`.
- F12. Per-pipeline node structure: receivers → `capabilitiesNode` → ordered chain of processors → `fanOutNode` → exporters; the fanout node is always inserted even for a single exporter (`createEdges`, graph.go:268-292).
- F13. The capabilities node aggregates `MutatesData` from processors and from the fanout/exporters and wraps the downstream consumer with `capabilityconsumer` so receivers see the pipeline's true capabilities (graph.go:314-340).
- F14. `internal/fanoutconsumer` fans out data to multiple consumers with smart routing: it clones only for mutating consumers, avoids sharing mutable data with read-only consumers, and skips wrapping when there is a single non-mutating consumer (internal/fanoutconsumer/traces.go:14-60).
- F15. Components are instantiated in reverse topological order after `topo.Sort`; cycles in the graph are reported as errors via `topo.DirectedCyclesIn` (graph.go:297-301).
- F16. `Graph.StartAll` starts components in reverse topological order with receivers started last (stabilized sort puts receivers first), so downstream components are ready before upstream ones; `Graph.ShutdownAll` stops in topological order (upstream first) so data can drain (graph.go:406-508).
- F17. Connectors bridge pipelines: `createNodes` type-checks each connector's exporter-side and receiver-side signals against `connectorStability` and errors if a connector is used as an exporter/receiver with no supported counterpart pipeline (graph.go:144-201); connector nodes are attached to both the exporting and receiving pipelines (graph.go:253-265).
- F18. Receiver and exporter nodes are shared across pipelines: `createReceiver`/`createExporter` reuse an existing node and add pipeline IDs to its `InstanceID` when the same component ID appears in multiple pipelines (graph.go:216-251).
- F19. `component.Component` defines the lifecycle `Start(ctx, host)` / `Shutdown(ctx)` with phases Creation → Start → Running → Shutdown (component/component.go:14-62).
- F20. Factories: base `component.Factory` (`Type()`, `CreateDefaultConfig()`, component/component.go:181-194); kind-specific factories add signal creation, e.g. `receiver.Factory` `CreateTraces/CreateMetrics/CreateLogs` plus stability getters (receiver/receiver.go:60-79), `exporter.Factory` (exporter/exporter.go:51-76), `extension.Factory.Create` (extension/extension.go:37-47).
- F21. Stability levels are `Undefined, Unmaintained, Deprecated, Development, Alpha, Beta, Stable` with text unmarshalling and log messages (component/component.go:109-179).
- F22. `graph.Host` implements `component.Host`, holds the builders, `AsyncErrorChannel`, module info and the status `Reporter`; `NotifyComponentStatusChange` forwards events to extensions and pushes `StatusFatalError` errors into `AsyncErrorChannel`, which terminates the collector's control loop (service/internal/graph/host.go:27-106, otelcol/collector.go:472-474).
- F23. Component status is reported during start/stop: `StatusStarting` before `Start`, a permanent error event on failure, `ReportOKIfStarting` on success, and `StatusStopping`/`StatusStopped` during shutdown (graph.go:441-507); the reporter is created in `service.New` (service.go:200-205).
- F24. Extensions are managed by `service/extensions`: startup/shutdown order is computed topologically from each extension's declared `extensioncapabilities.Dependencies()`, and dependency cycles are reported as errors (`computeOrder`, service/extensions/graph.go:31-66).
- F25. Pipeline configuration validation: at least one pipeline (unless `service.allowNoPipelines` gate), each pipeline needs ≥1 receiver and ≥1 exporter, processors must not be duplicated; the `profiles` signal is rejected unless its feature gate is enabled (service/pipelines/config.go:20-75).
- F26. Feature gates live in the `featuregate` module: gates have IDs and stages (Alpha/Beta), a `Registry` supports the `--feature-gates` flag, and alpha gates default to disabled (featuregate/gate.go, registry.go, examples_test.go).
- F27. `otelcol.NewCommand` builds the cobra CLI with subcommands for feature gates, components listing, `validate`, and config `print`, and overwrites resolver URIs from `--config` flags (otelcol/command.go:20-60).
- F28. Component instances are created lazily by `service/internal/builders` (`builders.NewReceiver` etc.) from config + factory maps, with a `nop` fallback type; deprecated type aliases log warnings (service/internal/builders/builders.go).
- F29. `internal/sharedcomponent` deduplicates component instances keyed by a shared config so a component is started and stopped exactly once across signal types (`LoadOrStore`, internal/sharedcomponent/sharedcomponent.go:16-55).
- F30. Data model: `pdata` provides `pcommon`, `ptrace`, `pmetric`, `plog`, `pprofile` packages; supported pipeline signals are traces, metrics, logs, and profiles (profiles behind `xpipeline`/feature gate).
- F31. The repo ships concrete components used by the core distribution: `otlpreceiver`, `otlpexporter`, `otlphttpexporter`, `debugexporter`, `batchprocessor`, `queuebatchprocessor`, `memorylimiterprocessor`, `forwardconnector`, `zpagesextension`, `memorylimiterextension`, plus `nop` receiver/exporter.
- F32. `cmd/otelcorecol` is a generated binary ("Code generated by go.opentelemetry.io/collector/cmd/builder. DO NOT EDIT") whose `main` wires `otelcol.CollectorSettings` with the five config providers and `components` factory set.
- F33. Module stability is declared in `versions.yaml`: stable module set (v1.x, e.g. `component`, `confmap`, `pdata`, `consumer`, `pipeline`) vs beta module set (v0.x, e.g. `service`, `otelcol`, `connector`, helpers).
- F34. `Collector.Run` registers SIGHUP always for config reload and SIGINT/SIGTERM only when graceful shutdown is not disabled; `Shutdown` closes `shutdownChan` and waits for `Run` cleanup via a `WaitGroup` (otelcol/collector.go:164-171, 450-457).
